### 3.2 会话 id 的生成与稳定性

四层机制，缺一层就 403 或 429：

1. **形状** `SESSION_RE = /^ses_[0-9a-f]{12}[0-9A-Za-z]{14}$/` —— `src/upstream.js:137`。
2. **编码** `SESSION_DESCENDING_RE = /^[0-9a-f]{9}f[c-f][0-9a-f]$/` —— `src/upstream.js:151`，匹配 `slice(4,16)` 那 12 个 hex。上游只放行「降序时间戳」`~(ts_ms<<12|counter)`、counter 1–63（低 12 位落在 `0xfc0–0xfff`）；升序 `ts<<12` 或 sha256 摘要即使 `ses_` 形状正确也 403（`src/upstream.js:139-150` 注释，实测 2026-10-17）。
3. **判定** `isCanonicalSession(id)` = 两个正则都过 —— `src/upstream.js:154-156`。
4. **重编码** `canonicalizeSession(signal)` —— `src/upstream.js:166-174`：`sha256('ses\0' + signal)`，取前 5 字节拼 48 位时间戳，counter 固定 `1n`（低 12 位 `0xffe`，落在窗口内），再取反、padStart(12,'0')，尾部 14 字符由 `base62Fixed(digest[6..16], 14)` 生成（`:176-186`）。**同一 signal 恒定同一 id**。
5. **铸造** `mintSessionId(ts)` —— `src/upstream.js:206-219`：`~(ts*0x1000 + seq)`，seq 每毫秒重置、从 1 递增，保证突发 mint 仍在 1–63 窗口内（`:200-205` 注释）。

`sessionForConversation(sessionId)` 是唯一对外入口 —— `src/upstream.js:278-287`：
- 已经是 canonical → 原样透传（`:279`）；
- 否则以 `sessionId.trim() || 'global'` 为 seed，先查 `session-map.json`（`:281-282`）；
- 都没有才 `canonicalizeSession(seed)` 并落盘（`:283-285`）。
- 持久化：`SESSION_MAP_FILE = 'session-map.json'`（`:228`），落在 `<dsh home>/our-free-model/`（`sessionStorePath` `:230-232`，`DATA_DIR_NAME` 见 `src/store.js:30`），写盘走 tmp + rename（`:249-276`），失败非致命（`:275`）。

为什么必须稳定：免费额度**按 session 计**，每请求新 id 会很快 429 且 retry-after 递增（`src/upstream.js:262-276` 注释、`src/http.js:9-12`）。

`truncateSession(value)` —— `src/upstream.js:585-590`，`MAX_SESSION_LENGTH = 256`（`:71`）。调用点：`src/http.js:380`（POST）、`src/http.js:555`（GET）。

## 4. SSE 读取

### 4.1 首字节嗅探：SSE vs JSON

不信 `Content-Type` —— 该网关实测会用非 `text/event-stream` 的 Content-Type 返回正常 SSE（`src/http.js:13-16`、`:176-183` 注释）。

- 窗口：`SNIFF_BYTES = 4096` —— `src/http.js:185`。
- 判据 `sniffBody(text)` —— `src/http.js:193-199`：
  - 去 BOM、`trimStart` 后为空 → `'empty'`；
  - 以 `:` 开头，或前 64 字符里出现 `^(?:data|event|id|retry)[ \t]*:` → `'sse'`；
  - 以 `{` 或 `[` 开头 → `'json'`；
  - 其余 → `'unknown'`。
- `readHead(stream, limit, {signal, timeoutMs})` —— `src/http.js:220-257`：同一 `TextDecoder` 全程复用（`:224`，避免多字节字符被切断），**一旦判出 sse 立即 break**（`:237`），所以短回答不会在嗅探窗口里干等到 deadline；异常时 `reader.cancel()` + `classifyStreamFailure`（`:241-243`）。
- 已读字节不丢：`replayStream(head)` 把 head.chunks 拼回流的头部再接后续 —— `src/http.js:307-330`，并暴露 `stream.cancel()`（`:327`）供 `readSse` 立刻断开。
- 非 SSE 分支：`readRemainder`（`:334-352`）用同一 decoder 续读；`json` 走 `JSON.parse`（`:428-433`），`payload.error` 再分类（`:434`）；非 json 且是 HTML → `CODE.client` 并提示「前置代理/WAF」（`:418-421`）；其余 → `CODE.server`（`:422`）。
- 空体：`response.body === null` 或 `shape === 'empty'` → `CODE.empty`（`src/http.js:398`、`:406`）。

### 4.2 行切分与事件组装（`readSse`，`src/http.js:439-563`）

- 字节 → 文本：`buffer += decoder.decode(value, {stream:true})`（`:537`）；按 `buffer.indexOf('\n')` 逐行切（`:538-544`）。
- 单行处理 `line(value)`（`:499-528`）：
  - 先剥 `\r` 与 BOM（`:500`）；
  - **裸 JSON 兼容**：行以 `{` 开头（或已进入 rawJson 累积态）→ 先 flush 上一条 data，再累积 rawJson 直到能 `JSON.parse`（`:501-509`）；解析出 `payload.error` 或 `payload.type === 'error'` 立刻 `classifyFailure` 抛出（`:508`）；
  - 空行 → `dispatch()`（`:510`）；
  - `:` 开头 → 心跳/注释，忽略（`:511`）；
  - 拆 `field: value`，只认 `data` 字段（`:512-517`）；
  - `data` 前先试 `completeData()`：兼容「省略空行分隔符」的对端（`:516`、`:492-498`）。
- 多行 `data:` 用 `data.join('\n')` 合成一条 payload（`:487`）。
- **`[DONE]`**：两条路 —— `dispatch()` 发现 `payload.trim() === '[DONE]'` 返回 true（`:493`），或行内 `valueText.trim() === '[DONE]'` 直接终止（`:519`）。终止即 `return`，后续字节不再读。

### 4.6 AbortSignal 取消路径

一条请求有四个可能的中断源，全部汇到 `controller.signal`：

1. 调用方断开：`req.once('aborted')`、`socket.once('close')`、`res.once('close')` 三选一即 abort —— `src/forward.js:638-641`；连接进来时已经断了也立即 abort（`:642`）。
2. 调用方 `signal`（宿主侧取消）：`options.signal.addEventListener('abort', onAbort)` → `controller.abort(options.signal.reason)` —— `src/adapter.js:442-443`。
3. 总时限：`policy.totalTimeoutMs`（默认 1_800_000 ms）到点 `expired = true; controller.abort()` —— `src/adapter.js:445-453`，默认值 `src/recovery.js:8`。
4. 传输层自身：`fetch` 的 `signal` 直接透传 —— `src/http.js:385`；`readSse` 的 `next()` 在 abort 时 `stop()` 并抛 `CODE.aborted` —— `src/http.js:469-472`。

分类上必须落到 `ABORTED` 而不是 `TRANSPORT`（后者可重试，会把用户主动取消变成重发）—— `classifyStreamFailure` `src/http.js:260-265`、`postStreamed` 的 catch `src/http.js:391-393`。流式回写阶段若已发头，`serveCompletion` 只把 `outcome` 记为 `aborted`（`src/forward.js:667-669`、`traceRequest` 的 `end('aborted')` `:88-95`）。

### 5.2 哪些重试、退避参数

- **本插件自己不重试上游请求**：`postStreamed` 一次一发，没有内层 for 循环（`src/http.js:379-437`）。
- 重试决策交给宿主，策略在 `providerRetryPolicy()` —— `src/adapter.js:75-89`：
  - `mode: 'normal'`、`maxRetries: 2`；
  - `retryableCodes: ['EMPTY_RESPONSE', 'SERVER', 'TIMEOUT', 'TRANSPORT']` —— `:82`；
  - `initialDelayMs: 700`、`maxDelayMs: 8000`、`jitterRatio: 0.2` —— `:86-88`；
  - 刻意**不含** `REGION_BLOCKED`（地域拒绝重试只烧额度）与 `RATE_LIMIT`（本车道 429 的 retry-after 递增，两次自动重试会把一道墙变成三道，`:77-81` 注释 + issue #13）。
  - 字段必须平铺在顶层，嵌进 `backoff` 会让宿主排程算出 `NaN`（`:64-74` 注释）。
- 对调用方声明「别重试」：`x-should-retry: false` 头 —— `src/forward.js:162`，条件是 `EAC_UPSTREAM_FAILED`/`NO_PROGRESS`，或 4xx 且不是 `rate_limit_error`；`retry-after` 由 `providerRetryAfterMs` 折算成秒 —— `src/forward.js:163`。
- 插件内部的「第二次尝试」不是重试同一请求，而是**续写**：`for (let attempt = 0; attempt < 2; ...)` —— `src/adapter.js:424`，第二轮的 payload 由 `recoveryMessages`/`continuationMessages` 重写（见 §6.2）。
- `Retry-After` 解析：只认纯数字秒 → 毫秒 —— `src/http.js:169-172`；调用点 `src/http.js:388`。
- 端口绑定另有一套重试（与本链路无关）：`BIND_ATTEMPTS = 4`、`BIND_BACKOFF_MS = 150`、指数退避 `backoffMs * 2 ** attempt` —— `src/forward.js:262-263`、`:296`。

### 5.3 failure.js vs recovery.js 分工

**failure.js = 「怎么把失败说出去」**（跨三种本地协议的失败搬运与状态码映射）

- `carryFailure(failure, kind)` —— `src/failure.js:2-12`：把任意错误洗成只含 `message`/`code`/`status`/`providerRetryAfterMs` 的白名单对象；`kind === 'aborted'` 强制 `code = 'ABORTED'`（`:4`）；`code` 必须匹配 `/^[A-Z][A-Z0-9_]{0,63}$/` 才保留（`:8`）；`status` 必须 400–599（`:9`）。原因：宿主把 failure 直接写进持久 session 事件，任何 `Error` 实例 / `NaN` / `undefined` 都会让整轮 abort（`src/adapter.js:731-737` 注释）。
- `forwardFailure(outcome, anthropic)` —— `src/failure.js:15-38`：`classes` 表把 code 映成 `[httpStatus, errorType]`（`:17-30`），`byStatus` 兜底（`:31`），`anthropic && type === 'server_error'` 时改 `api_error`（`:35`），输出 `{status, error, retryAfterMs, classified}`（`:33-38`）。
- 使用点：`failureReply()` —— `src/forward.js:159-166`（未发头才写 JSON，否则返回 false 让调用方走流内错误帧）。

**recovery.js = 「这一轮还能不能自己救回来」**（同轮内的续写/检查点策略）

- `RECOVERY_DEFAULTS` —— `src/recovery.js:6-11`：`maxContinuationMs 1_800_000`、`totalTimeoutMs 1_800_000`、`checkpointLimit 131072`、`maxOutputTokens 8192`。
- `recoveryPolicy(value)` —— `:13-22`：允许设置页下调，但每项都被 `Math.min(requested, maximum)` 封顶。
- `recoverable()` 共性判据 —— `:25-31`：策略开启 + 未过总时窗 + **有 reasoning** + **无 text** + **无 toolCall** + checkpoint 未截断 + reasoningText 非空。
- `canRecover()` —— `:33-35`：再加「没收到终帧」（断流）。`canRecoverSilentStop()` —— `:42-44`：反过来，**收到终帧但只有思考没有正文**（宿主会判空响应）。
- `recoveryMessages(messages, checkpoint)` —— `:46-63`：把 checkpoint 作为「未完成的草稿」注入一条 user 消息，指令里含「不要重开分析、最多 800 词、不要调工具」。
- `continuationMessages(messages, partialAnswer)` —— `:73-82`：命中 `max-tokens` 截断时用，把部分正文当 assistant 轮喂回去，只要求接着写。
- `checkpointFits()` —— `:85-95`：用字节数做保守余量（图片字段替换成占位），不宣称是 tokenizer 精确计数。
- `addUsage()` —— `:97-104`；`createBlockTracker()` —— `:107-130`：终态异常时把已开的块补 `block-end` 交还消费者（工具只组装不执行）。
- 编排点：`src/adapter.js:576-600`（判定 `interrupted`/`silentStop`/`maxTokensCut` 并排下一次续写）。

一句话：**failure.js 管「报」，recovery.js 管「续」**；两者都只读 outcome，不改 outcome。

## 6. deferred / recovery / push

### 6.1 deferred-response.js —— 推迟「提交响应头」

`deferStreamResponse(res, heartbeatMs)` —— `src/deferred-response.js:2-44`，返回 `{ response, commit, dispose }`（`:43`）。`response` 是 `res` 的 Proxy，拦截四件事：

| 被拦截 | 行为 | 行 |
|---|---|---|
| `writeHead(...args)` | 挂起期间只把参数记进 `head`，不真写；`status >= 400` 时**丢弃已缓冲的 body**（清 `writes`/`bytes`） | `:19-25` |
| `flushHeaders()` | 挂起期间静默吞掉 | `:26` |
| `write(...)` | 推进 `writes` 队列并累加字节，`>= 64 KiB` 立即 `commit()`；带 callback 时用 `queueMicrotask` 立刻回调（不让上游等） | `:27-35` |
| `end(...args)` | 先 `commit()` 再真正 `end` | `:36` |

`commit()` —— `:9-16`：`pending` 才动，先 `clear()` 停表，再 `res.writeHead(...head)`、按序 flush `writes`。

**触发场景（为什么要它）**：
1. 非流式端点在 `complete()` 返回前根本不写头，而 Linux 上客户端断开时 `ServerResponse#close` 可能来得太晚 —— 于是 `serveCompletion` 用 `req 'aborted'`/`socket 'close'`/`res 'close'` 三路提前 abort（`src/forward.js:632-641`）。
2. 错误要能「整段替换」：先 `writeHead(200)` 再发现是错误，就只能往流里塞错误帧；挂起 head 让 4xx 有机会改成正经 HTTP 错误码（`:22` 清 body 是同一目的）。
3. 提前于首字节暴露头会把「失败」写成 200（`src/forward.js:857-859` 注释里的 empty-200 问题）。

**超时**：没有独立超时；第一次 `writeHead` 时若 `heartbeatMs > 0` 就挂一个 `setTimeout(commit, heartbeatMs)`（`:23`，`unref` 掉）。默认 `heartbeatMs = SSE_HEARTBEAT_MS = 15000`（`src/forward.js:707`、`:325`）。⇒ **15 秒内既无内容 delta 也无心跳，头就会被强制提交**（commit 后心跳接管）。
`dispose()` = `clear()`（`:43`），在 `serveCompletion` 的 `finally` 调用（`src/forward.js:675`）；`res` 的 `finish`/`close` 也会自动 `clear`（`:41-42`）。

### 6.2 recovery.js 的触发编排（回答「什么时候续写」）

在 `src/adapter.js:576-600`：

- `interrupted`：没收到终帧（`canRecover`）→ 断流恢复；
- `silentStop`：收到终帧但只有思考、无正文（`canRecoverSilentStop`）→ 空停恢复；
- `maxTokensCut`：`reason.kind === 'max-tokens'` 且工具调用没断（`outcome.brokenToolCall !== true`）→ 用 `continuationMessages` 续写；
- 三者都在 `!recovering && policy.enabled` 下触发，且续写预算 `continuationBudget` 要过 `checkpointFits`（`:590`），否则只告警不续（`:592`）。
- 续写回合**禁用工具**：一旦上游仍回工具块，抛 `STREAM_CUT`（`src/adapter.js:540-543`）。

### 6.3 push.js —— 与本转发链路无关的 UI 推送通道

`createPushHub({logger, heartbeatMs})` —— `src/push.js:21`。它是一条给**插件自己的 Web 界面**用的 SSE 广播：

- `attach(req, res, hello)` —— `:51-68`：写 200 + `text/event-stream`（`:52-57`），先发 `: connected`（`:58`），可选 `hello` 事件（`:59`），登记 client，启心跳，`req/res` 的 `close` 都触发摘除（`:62-67`）。
- 推送内容：`sendTo(res, event, data)` 写 `event: <name>\ndata: <json>\n\n` —— `:69-77`；`emit(event, data)` 广播给所有连接 —— `:79-81`。**推的是插件自己的状态快照**（例如 `hello` 的负载由调用方给），不是模型 token，也不是上游事件。
- 语义：fire-and-forget，**无历史回放** —— 后连上的客户端只能从 `hello` 得知当前态（`:12-14` 注释）。
- 心跳 `HEARTBEAT_MS = 25_000` —— `:19`，`startHeartbeat` `:26-36`（写 `: ping\n\n`，顺手清掉已结束的 client），无人时自动停表。
- `dispose()` —— `:84-90`：热重载/卸载时把所有流 `end()` 掉，避免半开响应残留。

结论：转发主链路（`forward.js`→`http.js`→`stream.js`）不经过 `push.js`；后者只服务设置页/看板这类同源 UI。

### 7.3 node 直调 `src/forward.js` 的脚本骨架

不启 dsh 也能把转发链路拉起来：`complete` 是自己给的桩，`optimize`/`health`/`handleRequest`/`onTrace` 都可挂钩。

```js
// /tmp/ofm-forward-probe.mjs
import { startForwardServer, generateKey } from '/home/fish/projects_mine/dsh-our-free-model/src/forward.js'

const key = generateKey()
const server = await startForwardServer({

  complete: async (request, onChunk) => {
    onChunk?.({ type: 'reasoning-delta', text: '想一想…' })
    onChunk?.({ type: 'text-delta', text: 'ok' })
    onChunk?.({ type: 'usage', usage: { inputTokens: 3, outputTokens: 1 } })
    return { text: 'ok', toolCalls: [], usage: { inputTokens: 3, outputTokens: 1 }, truncated: false }
  },

  onTrace: e => console.log('[trace]', e.stage, e.outcome ?? ''),
  heartbeatMs: 5000,
})
console.log('port =', server.port, 'key =', key)
// curl -N -H "authorization: Bearer $key" ... http://127.0.0.1:<port>/v1/chat/completions
process.on('SIGINT', async () => { await server.close(); process.exit(0) })
```
