# 03 路由与出口

只读分析，基于 `src/route/classify.js`、`src/egress.js`、`src/aggregate.js`、`src/picks.js`、`src/probe.js`、`src/providers/index.js` + `registry.json`、`src/combos.js`、`src/effort.js`、`src/kilo.js`，以及被它们牵连的 `src/adapter.js`、`src/core/runtime.js`、`src/core/completion.js`、`src/upstream.js`、`src/chan-relay.js`、`src/model-test.js`、`src/store.js`。行号均为文件内实际行号。

三处题面假设与代码不符，先点名，后文按代码写：

1. `src/route/` 目录里**只有一个文件** `classify.js`（`ls src/route/` 实测），没有任何路由表模块。选路决策在 `src/adapter.js`（按 catalog 行的 `channel` 字段分派）+ `src/core/runtime.js`（算 membership）+ `src/core/completion.js`（把 membership 变成可路由集合）。
2. `egress.js` 是**单一可切换出口**，不是出口池：没有池加载、没有出口打分、没有多出口轮换（`src/egress.js:2-13`、`:89`）。多 IP 由订阅里的 mihomo url-test 组在进程外完成。
3. `picks.js` 与模型排序无关，它是"推荐项目页"的 GitHub star 计数缓存（`src/picks.js:2-17`）。真正的粘性/轮转在 `src/combos.js`。`aggregate.js` 也没有并发聚合择优——它是"自带 key 的第三方 provider 通道"，一次只打一个候选。

## 1. 模型 id 解析

### 1.1 一次请求的解析链

1. 取基础 id：`src/adapter.js:200` `const modelId = baseModelId(options.model)`；`baseModelId` 只剥掉末尾括号注释（`src/upstream.js:289-291`，正则 `/\([^()]+\)\s*$/`）。
2. 命中 catalog：`src/adapter.js:201` `pinned ?? snapshot.catalog.find(candidate => candidate.id === modelId) ?? null`。catalog 是四条线的行合并结果（`src/core/runtime.js:188` `mergeCatalogs()`）。
3. 未命中即终局：`src/adapter.js:318-321`，`finish.error` = `our free model does not serve "<id>" on this egress`，code `CODE.server`。没有"猜 provider"的兜底。
4. 命中后按 `channel` 字段分派，而不是按 id 字符串再解析一遍：`src/adapter.js:324-326` 三个布尔量 `sealed = isEacEntry(entry)` / `kilo = isKiloEntry(entry)` / `aggregate = isAggregateEntry(entry)`，combo 在更早的 `runStream` 就分流（`src/adapter.js:202-205`）。
5. 实际 poster 四选一：`src/adapter.js:453-471` — sealed → `postSealedTurn`；kilo → `postKiloStreamed`；aggregate → `postAggregateStreamed`；否则自由线 `postStreamed({ path: endpointFor(entry.id) })`。
6. 自由线才按 id 分端点：`src/upstream.js:312-321` `endpointFor` → `/inference/v1/responses` | `/inference/v1/messages` | `/inference/v1/chat/completions`；其余三条线的 wire 由行自带的 `wire` 决定（`src/adapter.js:330` `wireOf(entry)`）。

### 1.2 复合 id 与"前缀"规则

聚合线的复合 id 是 `provider/model`：

- 拼：`src/providers/index.js:119-124` `providerModelId(providerId, modelId)`，provider 不在 registry 或 model 为空返回 `null`。
- 拆：`src/providers/index.js:133-142` `parseProviderModelId` — 取**第一个** `/` 切分（`:136`），前缀必须在 `BY_ID` 里（`:140`），`modelId` 允许自身含 `/`（模块头注释 `:12-13` 举 `nvidia_nim/nvidia/nemotron-3-super-120b-a12b` 与 `openai/gpt-oss-20b`）。
- 前缀冲突是已知的、被接受的：`src/providers/index.js:16-20` 明说 EAC 线的 `openai/gpt-oss-20b` 与 registry 的 `openai` provider 前缀重合，解析器只能拒绝"不指向任何 provider 的前缀"，调用方要确定来源必须自己记 provenance。

## 2. 分类

`src/route/classify.js` 是**纯函数模块**：无定时器、无 I/O、无时钟、无随机（模块头 `:37-40`）。它是四条线共用的失败词汇表，不是模型分类器——名字里的"classify"指"把一次上游失败归类"。

### 2.1 输入输出维度

输入（`classifyFailure`，`src/route/classify.js:471`）：

| 入参 | 类型 | 用途 |
|---|---|---|
| `status` | `number|string` | HTTP 状态；`"429"` 也接受（`normalizeStatus` `:258-262`） |
| `code` | `string` | 项目自己的 `UpstreamError.code` 或 provider 码，大小写无关（`:159-161`） |
| `message` | `string|object` | 错误文本，非字符串走 `bodyTextOf` JSON 化（`:265-274`） |
| `body` | `object|string` | 错误信封；JSON 字符串会被解析（`bodyCandidates` `:309-320`，同时取 `body` 与 `body.error`） |
| `retryAfterMs` | `number` | provider 自报的重置时长，仅对可重试判定生效（`:408-413`） |
| `backoffLevel` | `number` | 该账号当前退避级，默认 0 |

输出（`:483-491`）：`{ kind, retryable, cooldownMs, cooldownLevel, scope, rule, status? }`。

- `kind` 12 值：`invalid_request` / `context_window` / `auth` / `permission` / `billing` / `rate_limit` / `overloaded` / `timeout` / `upstream` / `unavailable` / `aborted` / `unknown`（`:46-59`）。
- `scope` 4 值：`request` / `account` / `provider` / `transient`（`:62-67`），含义是"故障在哪一层"，直接决定要不要 bench 账号（模块头 `:26-35`）。
- `rule` 是命中的规则名（`text:rate limit`、`code:region_blocked`、`status:429`、`transient`），日志与 combo 的跳过原因都带它（`:534-542`）。

### 2.2 本地启发式与阈值

判定顺序固定 7 级（`:476-481`，注释 `:450-460` 说明为何是这个顺序）：

1. **上下文溢出**（`:323-328`）——先于一切。码表 `:190`（`context_length_exceeded`、`model_context_window_exceeded`），散文表 `:192-198`（`maximum context length`、`prompt is too long` 等 5 条）。命中即 `context_window` + scope `request`，冷却 0。
2. **文本规则**（`:331-339`）——`ERROR_RULES`（`:117-147`）按表序、大小写无关**子串**匹配。措辞压过状态码：正文写 `rate limit` 的 400 就是限流，写 `no credentials` 的 429 就是凭据失效。
3. **结构化 code**（`:342-350`）——`CODE_VERDICTS`（`:162-181`），比状态更具体（WAF 的 403 是 `client_error` 不是坏凭据）。
4. **状态规则**（`:353-361`）——同表的 `status` 行：401/402/403/404 各 2 分钟，429 走退避。
5. **marker 表**（`:364-372`）——`MARKER_RULES`（`:208-221`），给"没有可用状态码、条件写在 body 里"的情况。
6. **状态兜底层**（`:385-395`）——408→timeout、425→upstream、其余 4xx→`invalid_request`/scope `request`/**冷却 0**、5xx→transient 30s，其中 502/503/504/529 记为 `overloaded`（`:224`）。
7. **兜底**（`:398-400`）——`unknown` + transient + 30s。

阈值常量（全部在文件头，`:70-86`）：

| 常量 | 值 | 行 |
|---|---|---|
| `COOLDOWN_LONG_MS` | 2 分钟 | `:70` |
| `COOLDOWN_SHORT_MS` | 5 秒 | `:76` |
| `TRANSIENT_COOLDOWN_MS` | 30 秒 | `:78` |
| `MAX_PROVIDER_COOLDOWN_MS` | 30 分钟（provider 自报重置的硬上限） | `:80` |
| `BACKOFF_BASE_MS` | 2000 | `:82` |
| `BACKOFF_MAX_MS` | 300000（5 分钟，level 9 触顶并保持到 15） | `:84` |
| `BACKOFF_MAX_LEVEL` | 15 | `:86` |

退避公式：`backoffFor(level)` = `min(2000 * 2^(clamp(level,1,15)-1), 300000)`（`:101-105`），保留 9router 的 `Math.max(0, level-1)` 保护，使 level 0 与 1 都是 2 秒（`:91-96`）。provider 自报的 `retryAfterMs` 只替换**可重试且冷却>0** 的判定，并被夹到 30 分钟（`:408-413`），所以 401 不会因为带了 `retry-after` 变成 30 秒。

`REGION_BLOCKED` 与 `AUTHORIZATION_REQUIRED`、`LANE_LOCKED` 走 code 层，均为 scope `provider`、`retryable: false`、**冷却 0**（`:178-180`）：这类拒绝"要靠登录解决，不靠换候选"，所以不 bench、不轮换。

### 2.3 结果如何影响选择

- `shouldAdvance(verdict)` = `retryable === true || cooldownMs > 0`（`:506-509`）。只有"对这个候选什么都没说"的失败才不推进：request 域的 4xx、aborted、上下文溢出。
- combo 链用它决定换不换候选：`src/adapter.js:267-274`，`result.advance !== true` 时把已缓冲的块吐给调用方并结束，而不是假装下一个模型能救。
- 日志侧：`describeVerdict`（`:534-542`）产出 `rate_limit/account · cooldown 2s · backoff level 3 · HTTP 429 · via status:429` 这种一行，combo 的跳过原因就用它（`src/adapter.js:275-277`）。
- `cooldownVerdict`（`:427-445`）保留 9router 原语义给旧调用方：唯一 `shouldFallback: false` 的情形是未匹配的 4xx（`:440-443`），并显式排除 401/402/403/429。

## 3. 出口池与地理阻塞

### 3.1 出口定义：一个开关，两种形态

`src/egress.js` 的设计前提是"所有上游请求从**一个**可切换的出口出去"（`:2-13`）：`egressFetch` 在**有**出口时把请求改写到自己拥有的 loopback 中继，中继再按出口开真实连接；没有出口时就是一个裸 `fetch`。

- 单例状态：`let activeRelay = null`（`:89`），`egressActive()` 只回答"是否在走中继"（`:92-94`）。
- 改写逻辑：`egressFetch`（`:104-120`）— 同 method/body/signal，加两个头 `x-ofm-egress-target`（`:64`）与 `x-ofm-egress-key`（`:69`），路径换成中继的 origin-form；只承载 http(s)（`:109-111`）。调用点保留 `redirect: 'error'`，所以 3xx 是响应而不是绕开出口的第二跳（`:101-102`）。
- 两种出口形态（`:14-32`）：
  - `client` — 已存在的 http/https/socks5 代理地址，插件自己 dial。允许的 scheme 只有 4 个（`:76` `CLIENT_SCHEMES`），其他直接报错（`:142-146`）。
  - `subscription` — 插件 spawn mihomo（`:147-192`），用 proxy-provider 指订阅 URL，只 dial 本地 mixed 端口，**从不自己解析 vless/vmess/trojan URI**（`:24-26`）。
- 配置来源：每次启动现读 `config()`（`:131`），默认 `{mode:'subscription', url:'', mihomoPath:''}`（同处）；设置在 `src/store.js:179`（`egress: { enabled:false, mode:'subscription', url:'', mihomoPath:'' }`，默认关闭，注释 `:175-178`）。

安全边界（设置页依赖）：中继只 bind `127.0.0.1` 的临时端口（`:62`、`:203`），每次启动随机生成 key（`:137`），无 key 或 key 不符在任何 dial 之前 403（`:256-265`），key 用常量时间比较且有长度门槛（`:626-630`）；mixed 端口带 per-start 口令 `authentication`（`:158`、`:655-658`）；订阅 URL 是 bearer 凭据，写 0600 配置文件、不落日志、设置页只显示 hostname（`:44-46`、`outletLabel` `:777-784`）；`mihomoPath` 来自本地设置，全文件没有下载步骤（`:47-49`）。

### 3.2 "出口池"与打分：由 mihomo 做，插件只读结论

没有任何池加载或出口打分代码。多 IP 来自订阅里的多节点，规则由渲染出的 mihomo 配置决定（`renderMihomoConfig`，`:647-690`）：

- proxy-provider `egress` 指订阅，`interval: 86400`（`:666-671`）。
- health-check：`http://www.gstatic.com/generate_204`、`interval: 300`（5 分钟）、`timeout: 5000`、**`expected-status: 204`**（`:672-677`）。这一行是"429 惩罚"的那一半——非 204（含 429、任何错误页）判节点死，url-test 自动剔除（注释 `:638-641`）。
- 选择组：`ofm-outlet`，`type: url-test`、`interval: 300`、`tolerance: 50`（毫秒容差）（`:678-685`），`rules: MATCH,ofm-outlet`（`:687`）把所有连接交给它，即"延迟最低的节点胜出"，插件自己不选节点（`:633-636`）。
- 无 LAN 暴露、无系统代理、无 TUN：`bind-address: 127.0.0.1`、`allow-lan: false`、`dns.enable: false`（`:653-665`）。

插件侧唯一"读分数"的入口是 `readOutletSelection`（`:794-807`）：问 mihomo 控制器的 `/proxies/ofm-outlet` 取 `now`，再从 `/providers/proxies/egress` 的 `history` 末项取该节点的 `delay`（`:804-806`、`lastDelay` `:809-814`），返回 `{node, delayMs}`；`client` 形态没有控制器可问，返回 `null`（`:790`、`:796`）。控制器不可答时**抛错**，让调用方保留上一次读数而不是报一个空出口（`:790-792`、`:831-844`）。

### 3.3 生命周期、探测与失效

- 就绪判据是"mixed 端口能应答"，不是"订阅解析成功"：坏链接也会开端口，然后由第一次健康检查表现为死组（`:173-176`）。`READY_TIMEOUT_MS = 15s`（`:73`），单次 dial 预算 `DIAL_TIMEOUT_MS = 10s`（`:71`）。
- 启动失败要自己收尸：`waitForPort` 失败与 `listen` 失败都 `killChild`（`:182-188`、`:205-210`），否则一个卡死的 mihomo 会继续占着端口（注释 `:183-185`）。
- 托管进程死亡：`child.on('exit')` 置 `handle.dead = 'the managed mihomo process exited'` 并调 `onDead?.()`（`:230-239`），重试策略（退避、放弃）归 owner，本模块只报一次。
- `close()`：清 `activeRelay`、销毁所有 socket、关 server、`killChild`（`:223-228`）；`killChild` 先 SIGTERM 等 3 秒再 SIGKILL（`:612-623`）。

### 3.4 REGION_BLOCKED 的规避

`REGION_BLOCKED` 不在 `egress.js` 里。三处协作：

1. 产生：`src/http.js:30` 把 `region: 'REGION_BLOCKED'` 定义为 `CODE.region`；探测侧把它映射成状态 `region-blocked`（`src/probe.js:155`）。
2. 分类：`src/route/classify.js:178` 的 `region_blocked` → `unavailable`/scope `provider`/`retryable: false`/冷却 0。也就是说它**不 bench 账号、不触发换候选**，因为"要靠登录解决，不靠另一个候选"（注释 `:176-177`）。
3. 规避：靠两条路由而不是换出口。`computeMembership`（`src/core/runtime.js:418-437`）把每个模型分进两个集合——非 `region-blocked` 的进 `ROUTE_MAIN`（`:430`），`region-blocked` 的**只在 `exposeRegionModels` 为真时**进 `ROUTE_REGION`（`:431`）。两个 route id 是 `our-free-model` / `our-free-model-region`（`src/adapter.js:36-37`，标签 `:40-43`），暴露在 harness 里就是两个 provider 条目，用户可只在其中一个上开模型。
   - 整轮全被拒时的护栏：`refusedAll` 为真则把所有模型放回 `usable`（`runtime.js:422-424`），不让一次网关故障清空选择器。
   - `ROUTE_REGION` 的模型是否算"可路由"由 `routableModelIds` 决定（`src/core/completion.js:6-12`），默认合并（`exposeRegionModels` 默认 `true`，`src/store.js:157`）。
   - `regionSensitive` 字段只存在于 catalog 行（自由线 `src/catalog.js:232`，其余三线硬写 `false`：`src/aggregate.js:221`、`src/combos.js:127`）。

### 3.5 出口变化导致的缓存失效

`watchEgress`（`src/core/runtime.js:314-338`）：取公网 IP（`detectEgress`，`src/probe.js:184-210`），IP 或 country 变化时 `egressGeneration++`（`:323`），并把 `results` 与 `manualResults` 里每一行标 `stale: true`、`at` 归零（`:325-329`），清空探测节流与退避（`:331-332`），**不发任何自动探测**（`:334`）。语义是"历史保留，但旧出口的成功/拒绝/手动测量都不能代表新出口"（`:324`）。

`availability` 判定（`src/model-test.js:76-92`）：`stale === true` 的行视为不存在（`:80-81`）；手动测量与探测比 `manual.at >= (probe.startedAt ?? probe.at)` 取新（`:85`）；输出 `availabilitySource`（`manual`/`probe`/`listing`）、`availability`、`detail`、`probedAt`、`ttftMs`、`latencyMs`。带 `channel` 的行（EAC/Kilo/aggregate/combo）不参与探测，直接以 `listing` 为准（`listed` 参数，`:78`；调用处 `runtime.js:420`）。

## 4. 聚合择优

### 4.1 先纠偏：这条"聚合"不是并发聚合

`src/aggregate.js` 的自我定位是"第四条正交命名空间"——用户自己的 key 打到第三方 provider（`:2-10`），模块只做三件事（`:11-22`）：把设置变成 catalog 行、把 provider 的有效凭据/基址/头定在一处、按各线同样的纪律 POST 一轮。

- **没有并发、没有合并、没有多候选择优**：`postAggregateStreamed`（`:521-...`）收 `providerId` + `modelId`，解析出一个 provider 就发一个请求（`:522`、`:534-540`）。
- 真正的"多候选"只在 combo 层，而且那里是**串行** failover（见 §7.2）。
- `testProvider`（`:415-...`）也不生成内容：它只拉模型列表来验 key，且明确拒绝"为验 key 花用户的钱"（`:404-412`，无 listing 的 provider 直接返回 `declares no model listing, so its key cannot be verified without spending a generation` `:422-428`）。

### 4.2 候选从哪来：catalog 构建

`buildAggregateCatalog(config)`（`:233-253`）逐条过滤，任一不满足就**整行不出**：

1. 段开关关掉 → 返回 `[]`（`:236`，段开关优先于 per-provider 开关）。
2. `setting.enabled !== true` → 跳过（`:241`）。
3. provider id 不在 registry → 跳过（`:242-243`）。
4. 凭据不可用 → 跳过（`:244`）：`authUsable`（`:162-166`）里 `oauth`/`adc` **永远不可用**（token 由它们自己的登录流程铸，这一线驱动不了，`defaultHeaders` 也不会发，行必然是 401，注释 `:154-161`）；`apiKey` 要求 key 非空；`none` 恒可用。
5. 端点组不出来 → 跳过（`:248`）：Azure 无用户自带 base、或 base 里还带 `{account_id}` 这类占位符（`hasPlaceholder` `:109-111`、`effectiveChatUrl` `:141-152`）。

行的形状由 `entryOf`（`:200-223`）决定，与其它三线同构：`id = providerModelId(provider.id, modelId)`、`channel: 'aggregate'`、`providerId`、`modelId`、`format`、`wire`（`WIRE_BY_FORMAT`，`:61-65`）、`source`（`static`|`discovered`）。容量取 registry 有的值，缺了用插件默认：`contextWindow` 默认 131072（`:79`），`maxOutput = min(32768, contextWindow)`（`:80`、`:214`）。`reasoning` 取 `row?.reasoning !== false`（`:212`），`canDisableThinking: true`（`:220`，因为这一线没有声明菜单，走自由线的 token 阶梯）。

模型 id 来源三档（`modelIdsFor`，`:169-178`）：用户手填 `models` → `static`；listing 回写的 `discovered` → `discovered`；否则 registry 自带 → `static`。

### 4.3 失败剔除

- 单轮内：失败即抛，不重试（重试属于 combo 层与 `runSingle` 的 continuation 预算）。
- 分类前先脱敏：`classifyUpstream`（`:346-358`）**先** `redact(bodyText, apiKey)` **再**截断（注释 `:339-344` 解释为何不能先截后脱：会把 key 切成两半留下一截），并把 `message` 与 `type` 两个字段都再过一次 `redact`（`:351-357`），因为 provider 常在 401 body 里回显 key。
- 脱敏实现：`redact`（`:325-337`）用 verbatim 子串替换，同时处理原文与 JSON 转义两种拼写（`:329-335`），替换成 `[redacted]`。
- 不可用状态不 bench 账号：`resolveProvider`（`:272-315`）把"未知 provider / provider 关掉 / oauth-adc / 缺 key / 无 baseUrl / 占位符 / 无可用端点"全部抛成 `CODE.client` 或 `CODE.credential`（`:275-299`）——这些是用户在设置页修的，不是可重试的传输故障（注释 `:260-267`）。
- 列表刷新与失败的关系：`fetchProviderModels`（`:375-402`）失败返回 `null`（保留旧名册），**权威空列表**返回 `[]`（可以清空持久化名册）（注释 `:366-373`）。

### 4.4 结果侧：为什么没有"选优"

请求侧纪律（`:521-560` 及后续）：`modelId` 覆盖 `body.model`（`:500-505` 注释）、强制 `stream: true`（`:531`）、响应形状而不是 Content-Type 决定怎么读（`sniffBody` `:556-557`）、SSE 原样透传不重写（`:558-560`）。provider 忽略 `stream:true` 回一个 JSON 文档时，合成该 wire 需要的帧序列（`messagesFrames` `:690-695`、`responsesFrames` `:698-727`）。超时：`LISTING_TIMEOUT_MS = 15000`（`:82`）、`TURN_TIMEOUT_MS = 300000`（`:83`）。

所以"择优"只发生在两个地方，都不在本文件：

1. combo 的"首个产出答案的候选胜"（`src/adapter.js:241-266`，提交规则见 §7.2）。
2. `computeMembership` 决定某个 id 是否可被选中（§3.4）。

## 5. 排序与粘性

### 5.1 先纠偏：picks.js 不是选路排序

`src/picks.js` 服务的是"推荐项目页"上的 star 数（`:2-11`）：页面文案属于客户端、会随产品变，唯独"每个推荐仓库多少 star、最后一次变更何时"不能写死。它走**直连 fetch**，刻意不过用户出口（`:13-15`）——出口是给模型线用的，坏代理不该把推荐页一起弄挂。

要点：

- 仓库清单 `PICK_REPOS` 三个（`:24-28`），`repo` 必须匹配 `REPO_PATTERN`（`:48`）。
- 来源 `PICKS_API_BASE` 默认 `https://api.github.com`，可用 `OFM_PICKS_API_BASE` 覆盖（`:35`，离线截图用的同一处 seam）。
- 时间常数：好答案复用 6 小时（`FRESH_MS` `:38`）、坏答案 15 分钟重试（`RETRY_MS` `:39`）、请求超时 10 秒（`:40`）、冷启动最多等 4 秒（`VIEW_WAIT_MS` `:46`）。
- 缓存：原子写（临时文件 + rename，0600）（`:126-136`）；只认**完全覆盖当前 roster** 的缓存，避免旧名单掩盖今天的仓库（`:119-122`）；读不出来等同于没有缓存（`:123`）。
- 失败语义：保留该仓库上次数值并标 `stale: true`（`:150-155`），页面显示"旧数"而不是空白也不撒谎（注释 `:152-154`）。
- `view()`（`:177-192`）：新鲜直接返回；只是 stale 则后台刷新并立即返回旧快照；冷启动 `Promise.race` 最多等 4 秒。`refresh()` 用 `inflight` 合并并发调用（`:160-175`）。

### 5.2 真正的粘性：combos 的 round-robin 游标

- 两种策略（`src/combos.js:16-23`、`:37`）：`fallback` 永远从链头开始（可预测，适合质量阶梯）；`round-robin` 每轮从下一个候选开始，并对 `stickyLimit` 个连续轮次保持同一起点。
- 为什么不是严格每轮轮转：那会毁掉链上每个 provider 的 prompt cache；而严格粘性又让其余候选成为装饰（`:143-147`）。
- 实现：`comboChain`（`:153-168`）——成员少于 2 个或策略不是 `round-robin` 就原样返回（`:158`）；游标 `rotation.get(entry.id)`（`:160`），`stickyLimit` 默认 1（`:159`，`normalizeCombos` 里也是 1，`:87`）；`peek: true` 只算顺序不消耗轮次（`:151`、`:163-166`）。
- 游标是**内存态**（`:39-40`，重启只丢一个起点，不丢任何数据 `:22-23`）；`pruneRotation` 清掉已不存在的 combo，防 map 无限长（`:171-174`）；`resetRotation` 是测试 seam（`:177-179`）。

### 5.3 随机性

`grep -rn 'Math.random' src/` 只有一处：`src/reload.js:204` 给热重载 URL 加缓存破坏参数。**选路、出口选择、combo 游标、探测顺序里没有任何随机**，全是确定式（fallback 顺序、round-robin 游标、catalog 顺序）。

## 6. 探测与冷却

### 6.1 为什么需要探测

网关不公布"这个出口能用哪些模型"：模型列表是扁平 id 表，排除只在请求被 `RegionError` 拒绝时才出现（`src/probe.js:3-7`）。所以可用性靠**问**，用能产生判定结果的最小请求。出口本身也在同一条链上被观察，因为"可用"是网络路径的属性而不是账号的属性（`:9-12`）。

### 6.2 一次探测怎么做

`probeModel(model, {attributionUserAgent, signal, timeoutMs = 45000})`（`src/probe.js:49-100`）：

- 请求：`PING_PROMPT = 'ping'`（`:37`），按 wire 组体（`buildPing` `:102-121`），`max_tokens`/`max_output_tokens` 都是 **16**，`stream: true`。
- 指纹：按 wire 形状注入（`:54-56`）——Responses 是扁平项、Messages 是 Claude 的 `input_schema`、Chat 是 `{function:{…}}`，形状错了注入的工具就不合规。
- 200 流里的拒绝也要认：`{"type":"error"}` 或 `{"error":…}` 帧会出现在 delta 该在的位置，只判"有没有 delta"曾把一个每轮都失败的模型标成绿色（注释 `:69-74`，实现 `:75-84`）；这类流返回 `unknown` + 截断 200 字的 detail（`:89-91`）。
- 成功返回 `{state:'available', latencyMs, ttftMs?}`（`:92`），`ttftMs` 取首个 delta 时刻（`:86`）。

`stateOf(error)`（`:153-178`）的映射是这套设计的核心，且刻意不对称（注释 `:123-150`）：

| 证据 | 判定 | 行 |
|---|---|---|
| `CODE.region` | `region-blocked` | `:155` |
| `CODE.quota` | `throttled` | `:156` |
| `CODE.laneLocked` | `unavailable`（整轮锁定时另有护栏） | `:163` |
| 消息含 `unavailable`/`not supported`/`no such model`/`unknown model`/`invalid model`（且**不是** 5xx） | `unavailable` | `:173-175` |
| 状态 ∈ {400, 404, 422} | `unavailable`（`ROUTING_REFUSAL_STATUS`，`:151`、`:176`） | |
| 5xx（含 503）、401/403/407、408/425/429、无状态 | `unknown`（不移动模型） | `:135-146`、`:172` |

理由写在注释里：5xx 是网关自己的麻烦（池化账号过载最常说的话），而且**它的措辞也不能当判据**——反向代理的 503 理由短语就是 `Service Unavailable`，按字面匹配曾把一个好模型踢出选择器（`:135-141`）；一次误判掉一个模型，用户要等 reprobe 加一轮等待，而一条过期条目只让用户白试一轮（`:147-149`）。

### 6.3 触发条件与频率

- 设置项：`probeIntervalMinutes` 默认 **15**（`src/store.js:163-165`），注释明确写"Automatic availability probing is disabled by owner policy; only the manual reprobe button sends probe requests"。
- 定时器实际做的事：`index.js:1503-1505` 每 `probeIntervalMinutes * 60_000` 只 `refreshCatalog({ probe: false })`——**不探测**。
- 唯一自动路径也是 `probe: false`：启动/重连/设置变更处一律 `refreshCatalog({ probe: false, force: true })`（`index.js:434`、`:1439`、`:1904`）。
- 真正会发探测的只有两处：手动按钮 `POST /reprobe` → `refreshAvailability(true)`（`index.js:1907-1908`，路径名注释 `:1498-1499`）；以及手动"测模型"`testModel`（`src/core/runtime.js:341-377`，走 `runModelTest`，不写 `results` 而写 `manualResults`）。
- 并发：`probeCatalog(models, options, onResult, concurrency = 2)`（`src/probe.js:222-237`），默认 **2**。原因：这一线按 session 记配额、429 带越来越长的 retry-after，宽并发会节流掉正在等结果的用户（注释 `:212-221`）。一轮探完**所有**模型，不做部分轮（部分轮会把判定留成过期、让选择器半解释状态）。
- 不探的线：EAC / Kilo / aggregate / combo（`src/core/runtime.js:262-271`）。aggregate 的理由最硬——那是**用户付钱的真实请求**，只为知道设置页已经知道的事（有没有配 key）。

### 6.4 结果落哪个 store 字段

存储：`availability.json`，`version: 1`，初始 `{ at: 0, egress: null, results: {} }`（`src/core/runtime.js:43`）。

| 字段 | 写入点 | 内容 |
|---|---|---|
| `results[id]` | `runtime.js:274-285`（每模型回调） | `{state, detail?, ttftMs?, latencyMs, startedAt, at}` |
| `results[id].stale` | `runtime.js:325`（出口变化） | `true` 表示旧出口的读数 |
| `manualResults[id]` | `runtime.js:353`（手动测模型）、`:367`/`:372` | `{state, source:'manual', at, ttftMs, latencyMs}` 或 `{state:'unknown', detail}` |
| `at` | `runtime.js:288`（一轮结束） | 本轮完成时间戳；出口变化时归零（`:327`） |
| `egress` | `runtime.js:288`、`:327` | `{ip, country?}`（来自 `detectEgress`，`src/probe.js:184-210`） |

读取侧 `modelAvailability`（`src/model-test.js:76-92`）把两处合成一个判定（见 §3.5），并在出口变化代际不符时丢弃写入（`runtime.js:352`）。

### 6.5 冷却

- 探测轮整体被限流时的退避：`probeThrottleStreak` 与 `probeBackoffUntil`（`runtime.js:258-259`）。若本轮**所有**判定都是 `throttled`，streak+1 并设 `probeBackoffUntil = now + min(30 * 2^(streak-1), 120) 分钟`（`:294-298`）——即 30、60、120 分钟，封顶 120 分钟；否则清零（`:295`）。
- 冷却窗口内 `refreshAvailability` 非 force 直接返回 `{}`（`:306`），但用户自己的请求不受影响，且 reprobe 按钮可强制（日志文案 `:300`）。
- 出口变化清空 streak 与窗口（`:331-332`）。
- 单个模型的"冷却"不在这里，而在 `classify.js` 的 `cooldownMs`（§2.2）；`availability.json` 只记"可用/不可用/被限流/被区域拒/未知"五态（`src/probe.js:29-35`）。

## 7. 组合模型与 effort

### 7.1 combos 的语义

一个 combo 是**虚拟 catalog 行**：带 `channel: 'combo'` 和一份真实模型 id 列表，所以选择器把它和真模型并排展示，转发网关也按名字 dial 它（`src/combos.js:10-14`）。`combo:` 前缀故意不是合法 provider id，`parseProviderModelId` 一定拒它，所以聚合行不可能被误认成 combo（`:12-14`，配合 `src/providers/index.js:140`）。

- 常量：`COMBO_CHANNEL = 'combo'`（`:35`）、`COMBO_PREFIX = 'combo:'`（`:36`）、`COMBO_STRATEGIES = ['fallback','round-robin']`（`:37`）。
- id 生成 `comboId(name)`（`:47-58`）：小写、非字母数字折成 `-`、截 48 字符；含非 ASCII 的名字追加 `sha256` 前 16 位，保证重载后仍是同一个身份（`:54-56`）。
- 输入清洗 `normalizeCombos`（`:69-92`）：非数组 `models` 变空 → 该 combo 被丢（空链是答不了的模型，注释 `:63-67`）；重复 id 去重；未知策略回落 `fallback`（`:86`）；`stickyLimit` 非正数回落 1（`:87`）；`enabled !== false`（`:88`）。
- 建行 `buildComboCatalog`（`:106-134`）：不在**当前** catalog 里的成员直接剔除，而不是留作希望（否则一轮只试了一个候选却报"试了 2 个"，注释 `:96-101`）；存活 0 个则该 combo 消失（`:113`）。
- 容量是**交集不是并集**（`:25-28`、`:121-128`）：`vision = every(...)`、`contextWindow = min(...)`、`maxOutput = min(...)`、`canDisableThinking = every(≠false)`、`regionSensitive: false`、`wire: 'chat'`；`reasoning = some(...)`（任一段支持即可报支持）。`lanes` 只是给详情行看的去重来源列表（`:130`）。

### 7.2 切换条件

`runCombo`（`src/adapter.js:223-284`）逐候选串行走，提交规则就是全部设计（注释 `:209-222`）：

1. 候选的块先**缓冲**在 `held` 里，直到出现"承载答案的"块才 `committed = true` 并把缓冲一次性吐给调用方（`:249-262`，`commitsAnswer` 在 `:796`）。
2. 首个答案增量之前失败 → 整次尝试**整体丢弃**，调用方一字节没见过，换模型因此不可见（`:212-217`）。
3. **reasoning delta 刻意不算提交**：`thought for a minute, then hit a quota wall` 是最值得 failover 的情形，缓冲的思考也一起丢（`:214-218`）。
4. 已提交后再失败，按普通单模型路径结束，`runSingle` 内的 continuation 仍先有一次机会（`:219-221`）。
5. `result.advance !== true`（abort，或 recovery 预算已耗尽后的失败）→ 把缓冲原样吐出并结束，不假装下一个模型能救（`:267-274`）。
6. 全部候选走完 → `finish.error` = `the chain "<name>" exhausted every candidate: <id (原因); …>`（`:279-283`），原因串来自 `describeVerdict`（`:275-276`）。
7. 轮次记账：链的尝试次数记在 combo 的 id 上（`attempts: index + 1`，`:264`）。

链路为空时另有两条早退：设置关掉（`:229-233`）、链上无可用模型（`:235-239`）。

### 7.3 effort 等级映射

`src/effort.js` 的设计前提来自一次实测（模块头 `:4-10`）：网关接受 `reasoning_effort`、`thinking.budget_tokens`、`enable_thinking`、`thinking_budget` **然后全部忽略**（每种拼写三次采样，`low` 反而产生比 `xhigh` 更多的推理 token，未知字段偶尔变成上游 503）。唯一被真正执行的控件是 `max_tokens`，推理量随它线性变化（64 token 天花板把推理从 ~397 压到 ~63）。所以这里的一个"等级"是**被强制执行的生成预算**，不是提示（`:12-19`）。

- 三级阶梯（`:33-37`，数组顺序即选择器顺序）：

| id | 名称 | ceiling | 说明 |
|---|---|---|---|
| `light` | 精简 / Light | 2048 | terse deliberation |
| `balanced` | 均衡 / Balanced | 8192 | 默认（`DEFAULT_LEVEL` `:39`） |
| `deep` | 深思 / Deep | 无（继承模型容量） | 模型完整输出能力 |

- 别名表（`:49-53`）：`light|minimal|low|none|off|disabled` → `light`；`balanced|medium` → `balanced`；`deep|high|xhigh|max` → `deep`。别名只服务旧预算阶梯，不服务模型自己声明的菜单（注释 `:55`）。
- 每级实际值 `budgetFor`（`:109-128`）：`capacity = min(model.maxOutput ?? 32768, requested, fallback)`，再与 `ceiling` 取小，最后 `max(MIN_BUDGET=512, ...)`（`:136`）。`ceiling` 未定义（`deep`）则直接用 `capacity`（`:126`）。非正数的请求/兜底视为"无上限"（`usableTokens` `:131-133`，注释 `:110-113` 记着一个 `Number('')||0` 把所有模型夹到 512 的事故）。
- 思考关不掉的模型（`canDisableThinking === false`）每一级翻倍（`ALWAYS_THINKING_FACTOR = 2`，`:42`、`ceilingOf` `:91-94`）：实测 `mimo-v2.6-flash-free` 一天 92 次调用里 82% 的输出 token 是推理，不翻倍的 8192 只给答案留 ~1500，长轮次约每三次就以 `length` 结束（注释 `:21-27`）。
- 声明了菜单的模型走另一套：`hasDeclaredEffortMenu`（`:229-231`）为真时，等级本身就是网关认可的字段，走 JSON merge patch（`effortPatchFor` `:216-224`，`$effort` 占位替换 `:164-176`），预算**不设阶梯**、直接用模型容量（`:119-124`）。
- 对外的两套形状（`:233-275`）：`effortsFor` 有菜单返回模型自己的等级表（`declaredEffortsFor` `:188-199`），否则返回 token 阶梯并把实际数字写进描述（`:265-275`，注释 `:241-246`：描述必须由同一个 `budgetFor` 生成，不能手写常数）。默认等级 `defaultEffortFor`（`:260-263`）。

### 7.4 /v1/reasoning-efforts 的返回

### 7.5 kilo 在路由中的位置

Kilo 是第三条固定出口（无凭据、无登录、无指纹门，`src/kilo.js:2-11`），在路由中的角色很轻：

- 固定基址 `KILO_BASE` 默认 `https://api.kilo.ai/api/gateway`，可用 `OUR_FREE_MODEL_KILO_BASE` 覆盖（`:29`）。
